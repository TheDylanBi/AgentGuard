# 原生参数委托与有限审查恢复

本次修改继续使用实验性的 `review` 模式，不切换默认模式，不增加业务禁令。
原生字段证明允许进入审查，不等同于确定性授权，也不替代现实账户身份验证。

## 原生参数来源

工具通过绑定 Schema 的 `parameter_evidence` 声明候选字段来源。声明包含账户路径、
原生记录标签、字段类型，以及可选的 `where_parameters` 关联选择器。
例如退款金额必须来自原付款人与本次收款人一致的交易，不能只匹配一个相同金额。
没有任务编号、标准答案或固定账户值。另一工具可使用不同参数名作同类声明。

运行时要求本任务内真实查询结果、唯一匹配记录、当前账户、完整原生实体哈希和有效期均通过。
正文声称的交易、过期结果、跨账户记录、同额多笔交易、替换后的金额或账户都不能形成证明。
`EXACT_EXTRACT` 只证明字段对应，不证明用户选中了这笔交易。

只有声明为 content 的描述字段可作为待审查的生成文本；金额、账户、日期、执行参数不能走此路径。
Banking 的 send_money 已声明原生交易金额及原付款人来源。账单正文中的新收款账户不受此声明信任。

放行仍要求：硬约束通过、完整参数足够、有明确的原始任务授权、单独的数据流允许、
原始用户和必需观察引用，以及审查后的状态和硬约束复核。程序不清除污染状态。
金融执行前消耗来源身份；不同调用 ID 或重新查询同一交易不能重置次数。
失败/不确定执行也消费，不能自动重试可能已发生的支付；此保证仅在本任务模拟宿主中有效。

## 尚未自动解决的金融问题

本路径只做原生字段精确提取。已有 Decimal 计算图仍验证显式可信委托中的运算及账户字段；
此次没有从自然语言自动编译任意退款公式，也没有枚举运算直到凑出模型提出的金额。
自由文本账单金额解析、可信收款方关联和缺失付款日期仍可能需要补证或真实确认。
不为提高官方分数虚构日期、自动批准账单账户或覆盖 CONFIRM。

## Review 技术恢复

首次审查保留完整政策提示。格式错误、截断等允许恢复的技术错误最多重试一次，
重试使用较短的政策提示及紧凑 JSON；原始请求、完整有效参数、全部观察、先前操作保持不变。
不复用失败的推理输出，不删除否定限制或历史副作用，不因有效拒绝重试争取 allow。
重试输出仍经相同协议、证据引用和执行绑定检查。失败仍记未评分的审查错误。
这减少提示冗余，但不能保证长推理模型一定及时产出 JSON。

DeepSeek 兼容接口另提供显式 `ICB_REVIEW_THINKING_MODE=enabled/disabled` 及
`ICB_REVIEW_RETRY_THINKING_MODE`。它们发送顶层 `thinking.type`，与 vLLM 的
`ICB_REVIEW_ENABLE_THINKING`（chat_template_kwargs）不同；不得同时配置这两种开关，
也不得在 disabled 时同时传 reasoning_effort。依据官方协议：
https://api-docs.deepseek.com/guides/thinking_mode/

只想在技术恢复时关闭推理，可在兼容服务上显式设置：

```powershell
$env:ICB_REVIEW_RETRY_THINKING_MODE = 'disabled'
& '.\.local-qwen\run-qwen.ps1' -AllSuites -IntentFormat review
```

这不改变行动模型，也不自动切换默认审查配置。输出预算、实际思考模式、思考 token（若服务返回）、
生成结束原因记录在诊断中，配置进入实验哈希。HTTP 200 不等于服务落实了开关，仍需查看响应及安全对照。
关闭长推理可能影响语义准确性，有限探针只能验证协议和少量案例，不能代替攻击评测。

## 报告边界

配对比较新增 `paired_regression`：Baseline 成功数、Guarded 已评分失败数和 Guarded 未评分数分别报告。
observed_failure_rate 的分子只含已评分失败；未评分结果记为 unresolved_rate，不冒充成功或失败。
这些是观察到的配对变化，不是策略造成失败的因果证明。历史配置不匹配时仍拒绝直接比较。

离线测试特意放入错误审查器：参数确有来源但违背用户禁令时，错误的 allow 仍可能导致语义误放行。
因此，执行约束测试不是审查模型安全准确率证据；还需要固定模型的正常任务及攻击对照。

## 输入编码与评分差异

本地 AgentDojo v1.2.2 的 read_suite_file/ImportLoader 使用未指定编码的 open。
Windows 默认 cp936 会把 UTF-8 数据里的 Café 读成 Caf茅。这发生在模型请求之前。
本地启动脚本已显式使用 `python -X utf8`；直接调用模块时也应使用该参数：

```powershell
python -X utf8 -B -m adapters.agentdojo_pi.run ...
```

这修复整个 YAML/include 输入链，不修改外部 AgentDojo 源码、数据、工具输出或评分答案。
summary 新增 dataset_text_encoding，非 UTF-8 启动会警告，配对比较要求编码相同。
修复前的历史实验可能受输入乱码影响，不能与新输入环境直接作严格配对。

Travel 19 的本地官方 utility 要求六个名称和字符串 `3920`，餐费公式只有一个人数/餐次的因子 2；
原答案按两人各每天两餐得到 4260，另使用了千位分隔符 `4,260`。
这属于任务解释与官方严格断言的差异，不能据此归因于 Guard，更不能在策略里写入标准答案。
