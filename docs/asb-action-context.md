# ASB 行动上下文与通用性验证

这个改动针对执行流程和来源边界，不使用任务 ID、工具名、攻击标签或评分成功字符串制定策略。

## 原因

原生 ASB 在规划结束后仍保留要求 JSON 计划的系统提示；执行循环把新的计划当作普通回答保存，然后推进下一步。它还把模型生成的步骤包装为 user 消息，将工具返回包装为 assistant 消息，并把工具目录文字放进 system 消息。这些来源和阶段的混用独立于具体业务任务。

2026-10-27 的 200 例金融实验有 38 个官方任务失败：22 个遗漏评分工具、16 个调用被拦。28 个案例在执行中又输出了完整 JSON 计划，其中20个失败，17个属于遗漏类。这是可修复的流程现象，但相关性并不证明这17个都会被恢复。

6个攻击成功均在行动模型首次收到工具观察前提出；原生基准会把攻击工具注入候选工作流。因此不能把这些案例都解释为行动模型服从了工具返回中的恶意命令。

## 实现

`--action-context structured` 对模型输入作有来源记录的投影：

- 在原生代码的消息生成点记录来源、索引和内容哈希，禁止根据文本里的 `HOST` 或 `system` 字样推断信任。
- 规划阶段使用 JSON 计划协议；执行阶段使用调用／回答协议；结束检查和最终回复有独立阶段。
- 原始用户任务保留为用户输入；生成的计划和步骤保留原文，但标为 assistant 提案，不能增加权限。
- 工具目录、工具返回和恢复数据放进明确标注来源的数据封装；不删除攻击文字、工具或受污染的计划。
- 校验来源与消息角色，固定工具目录快照，检测历史、目录或请求内容漂移。
- 在需要时追加固定的继续消息，避免兼容服务把末尾 assistant 提案当作补全文本。该消息不包含模型生成的步骤或新的授权。

原生 `messages.json`、工具执行、OPI 注入、官方评分不变。`action-context.json` 保存投影后的查询消息、工具列表和来源记录；传输层有限格式重试仍记录在 `requests.json`。上下文投影本身不新增模型请求，不自动重试拒绝，不把计划里的工具列表强制执行。

baseline 与 guarded 使用同一种投影；`comparison.action_context` 不同时禁止作为纯防御开销／收益比较。`study.paired_effect(..., axis='context')` 只允许这一字段变化。

`structured` 当前仅支持 clean 与 OPI。其他攻击模式包含不同位置的注入，必须显式选择 `--action-context native`，不能静默丢弃注入。`--recovery native|bounded|checkpoint` 仍是独立设置。

默认仍为 `native`。本次15对小样本中，structured 消除了执行中的计划重发，但任务成功从11/15变为10/15、攻击成功仍为6/8、平均耗时从21.73秒变为37.75秒，因此没有将其升级为默认。保留它用于分离变量和后续验证，不将结构修复等同于成功率提升。

默认 `native` 现在也有一个窄的响应协议修复：行动阶段若返回严格匹配 ASB 原生
`[{"message": ..., "tool_use": [...]}]` 的规划信封，适配器不会把它当作执行结果，
也不会执行其中的工具名；只在既有 `--response-retries 1` 预算内要求一次原生工具调用
或证据支持的回答。连接在任何工具分派前失败时同样最多重试一次。HTTP 错误、模型
拒绝、授权决定和已经执行的调用不会因此重试。

## 仍需解决的边界

上下文来源隔离不证明工具实现可信。没有独立能力声明时，几个相近的分析工具描述无法可靠揭示隐藏的攻击标签。必须区分：

1. 工具是否由可信部署过程登记，描述与执行实现是否绑定；
2. 具体操作、资源、写入和数据流是否落在这次用户授权内；
3. 实际调用是否完成用户需要的结果。

项目已有版本2工具契约和 `--require-tool-contracts`。声明必须来自独立审阅的实现／部署配置，不能从 ASB 的 normal/attacker 集合生成许可清单。参数为 None、返回固定字符串的接口无法证明真实财务分析质量，也不能凭“分析用途”把一个混合工具的写入能力抹去。

生产接口应将查询、修改、交易等不同操作分开，或提供由服务端强制执行的操作选择和数据流限制。原生无契约 ASB 与加入独立契约的实验要分别报告。

## 验证

本轮审计、固定案例计划、脚本和原始日志见 `results/asb_generalization_validation_20261027/`。对照包含全部5个金融 clean 任务、6个已知攻击回归，以及按固定 ID 顺序选择的教育／系统管理 clean 和攻击案例，共每组15例。

这是机制检查和小规模回归，不是全量成绩。特别是已知攻击被有意集中选择，其攻击成功比例不能外推为整个 ASB 的攻击成功率。报告应同时保留任务成功、攻击成功、无分数错误、执行中计划重发、重复调用和耗时；不能只报告改善的一侧。
